# Сервис генерации

Принимает заказ на генерацию, списывает токены, отправляет задачу провайдеру по цепочке ног, при отказе всех ног возвращает токены. Каждое движение денег происходит ровно один раз.

Стек: Python 3.13, FastAPI, SQLAlchemy 2 (async, asyncpg), PostgreSQL 16, Alembic, httpx, pytest.

## Запуск

```bash
docker compose up --build
```

Поднимаются:

- `db` - PostgreSQL;
- `migrate` - одноразовый контейнер, применяет миграции и завершается;
- `app` - сервис на `localhost:8000`, `uvicorn --workers 4`, стартует после успешных миграций;
- `alpha`, `beta` - фейковые провайдеры на `8001` и `8002`.

Секрет вебхуков по умолчанию `dev-secret`, меняется через `WEBHOOK_SECRET`. Таймаут провайдера по умолчанию 60 секунд, для ручных проверок удобно `PROVIDER_TIMEOUT=10 docker compose up`.

Сид создаёт каталог моделей из задания и пользователей 1, 2, 3 с нулевым балансом. Токены появляются только через вебхук оплаты:

```bash
BODY='{"payment_id":"p1","user_id":1,"tokens":100,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac dev-secret | awk '{print $NF}')
curl -X POST localhost:8000/webhooks/payments \
  -H "X-Signature: $SIG" -H "Content-Type: application/json" -d "$BODY"

curl -X POST localhost:8000/generate -H "Content-Type: application/json" \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"cat","ref_images":[]}'
```

Поведение провайдера меняется на лету:

```bash
curl -X PUT localhost:8001/config -H "Content-Type: application/json" \
  -d '{"fail_rate":1,"fail_type":"technical","delay_min":1,"delay_max":2}'
```

Поля: `fail_rate` (0..1), `fail_type` (`technical` | `moderation` | `payload`), `sync_error` (`"503"` | `"timeout"`), `duplicate` (вебхук дважды одновременно), `drop` (вебхук не приходит), `delay_min`, `delay_max`. Поздний ответ: задержка больше `PROVIDER_TIMEOUT`.

## Тесты

Нужна база из compose:

```bash
docker compose up -d db
uv sync
uv run pytest -v
```

Тесты создают отдельную базу `app_test`, накатывают на неё миграции и перед каждым тестом очищают задачи, попытки и журнал. Приложение запускается в процессе через `httpx.ASGITransport`, база настоящая, поэтому конкурентные запросы действительно конкурируют в PostgreSQL. Отправка провайдеру подменена, вебхуки тест шлёт сам с подписью: результат не зависит от случайных задержек. Сторож вызывается вручную после сдвига дедлайна в прошлое.

| Тест | Что проверяет |
| --- | --- |
| `test_concurrent_payment_webhooks_credit_once` | 20 одновременных одинаковых вебхуков оплаты дают одно начисление |
| `test_concurrent_failed_on_last_leg_refund_once` | 10 одновременных `failed` на последней ноге дают один возврат |
| `test_first_leg_fails_task_completes_on_second` | отказ первой ноги, завершение на второй, две попытки в истории |
| `test_late_completed_while_task_alive_is_accepted` | правило 6, поздний ответ до финального статуса |
| `test_late_completed_after_refund_is_ignored` | правило 6, поздний ответ после возврата |

## Миграции

В compose миграции применяет контейнер `migrate`. Локально:

```bash
uv run alembic upgrade head
```

Новая миграция схемы: изменить модели в `app/models.py`, затем

```bash
uv run alembic revision --autogenerate -m "smth"
```

сгенерированный файл обязательно проверить глазами (autogenerate не видит часть изменений, например CHECK) и применить `alembic upgrade head`. Миграция данных пишется вручную через `alembic revision -m "описание"`, таблицы в ней описываются через `sa.table`, а не импортом моделей, чтобы миграция не ломалась при будущих изменениях моделей. Уже применённые миграции не редактируются.

## Модель данных

- `users` - баланс, `CHECK (balance >= 0)`.
- `models`, `legs` - каталог и цепочки ног.
- `tasks` - задача: `processing`, затем `completed` или `failed`. Финальный статус не меняется.
- `attempts` - попытка на конкретной ноге: `sending` -> `sent` -> `completed` | `failed` | `timed_out` | `superseded`. Хранит провайдера, тип ошибки, время, дедлайн.
- `ledger_entries` - журнал: `topup`, `charge`, `refund`. Уникальные ограничения `payment_id` и `(task_id, kind)`.

Статусы хранятся строкой с CHECK, а не ENUM: так их проще менять миграциями.

## Ровно один раз

Гарантию даёт база, а не проверки в коде, поэтому она не зависит от числа воркеров.

**Начисление.** Строка `topup` вставляется через `INSERT ... ON CONFLICT (payment_id) DO NOTHING RETURNING id`. Из одновременных дублей вставку получает один запрос, остальные ждут на уникальном индексе и после коммита первого получают пустой результат. Баланс увеличивается, только если вставка вернула строку, и в той же транзакции. Повтор отвечает 200, чтобы платёжный провайдер не слал ретраи.

**Возврат.** Тот же приём по ограничению `(task_id, 'refund')`. Кроме того, все события по задаче обрабатываются под `SELECT ... FOR UPDATE` на строке задачи: из 10 одновременных `failed` первый переводит попытку в `failed` и делает возврат, остальные после получения блокировки видят, что попытка уже не активна, и ничего не делают. Уникальный индекс остаётся второй страховкой.

**Списание.** `UPDATE users SET balance = balance - price WHERE id = ... AND balance >= price` атомарно проверяет баланс и списывает. Списание, задача и первая попытка создаются в одной транзакции под блокировкой пользователя, поэтому лимит в 3 активные задачи не обходится параллельными запросами.

Баланс и строка журнала всегда меняются в одной транзакции, поэтому баланс всегда равен сумме журнала. Проверка:

```sql
select u.id, u.balance, coalesce(sum(l.amount), 0)
from users u left join ledger_entries l on l.user_id = u.id
group by u.id;
```

Сумма возврата берётся из строки `charge` этой задачи, а не из текущей цены модели: если цену изменят, пока задача в работе, вернётся ровно списанное.

## Конкурентность и блокировки

Все изменения задачи и её попыток (вебхук, сторож, результат синхронной отправки) происходят под `FOR UPDATE` на строке задачи. Попытка читается уже после получения блокировки, чтобы решение не принималось по устаревшему статусу. Порядок блокировок везде один: сначала задача, потом её попытки и пользователь. Это исключает взаимные блокировки.

HTTP-запрос к провайдеру выполняется вне транзакции: попытка коммитится заранее в статусе `sending` с дедлайном, затем идёт запрос, затем отдельной транзакцией под блокировкой задачи записывается `sent` или переход на следующую ногу. Транзакция не держится открытой, пока провайдер отвечает.

## Сторож

Запускается в каждом из 4 воркеров через `lifespan`. Раз в 2 секунды выбирает активные попытки с истёкшим `deadline_at` (запрос попадает в частичный индекс по активным статусам) и для каждой берёт задачу через `FOR UPDATE SKIP LOCKED`. Если задачу держит другой процесс, она пропускается до следующего круга. После блокировки статус и дедлайн проверяются заново, поэтому несколько сторожей не задваивают работу. Время сравнивается по `now()` базы, а не по часам воркера. Просроченная попытка получает `timed_out` и дальше обрабатывается так же, как отказ `technical`.

## Падение процесса посреди обработки

Обработка вебхука выполняется в одной транзакции.

- **Падение до коммита.** PostgreSQL откатывает транзакцию целиком: не бывает строки в журнале без изменения баланса или смены статуса без возврата. Повторный вебхук провайдера обработается с нуля. Если провайдер повторять не станет, попытка останется активной, сторож по дедлайну сочтёт её неудачной и поведёт задачу дальше.
- **Падение после коммита, до ответа провайдеру.** Провайдер повторит вебхук, обработчик увидит, что попытка уже закрыта, и только залогирует дубль.
- **Падение после коммита, до отправки на следующую ногу.** Следующая попытка уже записана в статусе `sending` с дедлайном. Сторож её подберёт.
- **Падение в `/generate` между коммитом и запросом к провайдеру.** То же самое: попытка `sending` с дедлайном, её подберёт сторож.

Состояние в памяти процесса не используется, всё восстанавливается из базы.

## Поздний completed (правило 6)

Правило: **поздний результат принимается, пока задача не в финальном статусе; после финального статуса он только логируется.** Финальный статус не меняется никогда, поэтому задача не может получить и результат, и возврат.

- **Сторож закрыл попытку, задача ушла на следующую ногу и ещё не завершена.** Деньги списаны, возврата не было, результат готов. Задача становится `completed` с этим результатом, активная попытка на другой ноге получает `superseded`. Если её провайдер ответит позже, задача уже финальна, и ответ будет проигнорирован.
- **Ноги кончились, задача `failed`, деньги вернулись.** Поздний результат не выдаётся, деньги повторно не списываются, факт пишется в лог. Повторное списание после возврата было бы хуже: баланс мог быть уже потрачен, а клиент уже увидел финальный статус.

## Решения по неоднозначным местам

- Начисляются только оплаты со `status = "succeeded"`, остальные статусы принимаются с ответом 200 и игнорируются.
- Синхронная ошибка отправки (не-202 или ошибка соединения, включая таймаут) записывается в историю как `sync_error` и обрабатывается как `technical`.
- После отказа `moderation` пропускаются все оставшиеся ноги со `skip_on_moderation`.
- Вебхук провайдера сверяется с провайдером попытки: `beta` не может закрыть попытку `alpha`.
- Вебхук может прийти раньше, чем записан `sent`, поэтому `sending` тоже считается активной попыткой.
- Фейковые провайдеры хранят настройки в памяти и работают в один процесс. Правило 7 касается основного сервиса.
